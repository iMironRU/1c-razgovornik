# Гайд по стилю серии «Школа 1С-инженеров»

> Единый канон письма для книг серии. Claude Code и редакторы-сабагенты
> используют этот файл при написании и проверке параграфов.
>
> **Ориентир — советский академический учебник:** уважительный тон, линейное
> чтение, длинные связные фразы, ASCII-схемы. Предмет чтения — код и метаданные
> 1С. По умолчанию канон рассчитан на новичковый трек; книги для опытных
> читателей (переход с других языков, специальные темы) добавляют свою надстройку
> в конце файла, не отменяя ядро.
>
> Статус: канон v0.2.1 (адресация «мы»+«вы» утверждена). Все книги серии
> выровнены; детерминированную часть канона проверяет `scripts/style-lint.py`
> (см. §10 и docs/integration-roadmap.md §9).

---

## 1. Адресация

- Авторское **«мы»** для совместного рассуждения: «рассмотрим», «вернёмся к
  примеру», «соберём картину». Читатель идёт рядом с автором, а не получает указания.
- **«вы»** — при прямом обращении: «обратите внимание», «попробуйте проследить».
- **«ты» не используем** — оно уводит от интонации учебника.
- Без пряток за «читатель», «пользователь», «разработчик» в роли подлежащего там,
  где речь о том, кто читает книгу.

## 2. Структура параграфа

Один параграф — **одна тема**. Появилась вторая принципиально новая — сигнал
разбить на два (см. §5, «одно новое за раз»).

Рекомендуемый объём: 1500–3000 слов; мостиковый параграф — 500–1000.

1. **Открытие** — связь с предыдущим параграфом и постановка нового вопроса
   (образ или вопрос, ставящий проблему).
2. **Содержательные разделы** (5–9), нумерованные: `## 1. Название`. Каждый
   закрывает одну подмысль.
3. **«Главное в одном абзаце»** — плотный смысловой повтор ключевых мыслей в
   устной форме (не tl;dr и не пересказ дорожной карты).
4. **Контрольные вопросы** — до 5–7, проверяют материал этого параграфа.
5. **Упражнения** — лестница уровней: трассировка → копия → ловушка → чужой
   код / чужая форма.
6. **Ответы в трёх уровнях** — уровень 0 (на пальцах), 1 (основной), 2
   (экспертный конспект) + разбор каждого упражнения.
7. **Мостик** — формулирует ожидание от следующего параграфа, не пересказывает тему.

## 3. Голос и тон

- Без канцелярита: «следует отметить», «представляется целесообразным»,
  «осуществляется», «производится» — нельзя.
- Активный залог, где возможно. Пассив — только по действительной необходимости.
- Без пустых усилений: «по сути своей», «безусловно», «несомненно», «очевидно».
- Без шаблонных зачинов «В данном параграфе мы рассмотрим…».
- **Длинные связные фразы — норма** классического учебника. Ориентир длины —
  10–18 слов, но связный период длиннее допустим; запрещён рубленый,
  телеграфный стиль.
- Энергия: между предложениями читатель должен чувствовать движение. Где провисло —
  переписать.

## 4. Метафоры и парная строгая формулировка

- Метафора — **несущая стенка** объяснения, не украшение. Если её можно убрать
  без потери смысла — убрать.
- **Парная строгая формулировка обязательна.** Каждый яркий образ немедленно
  сопровождается строгой версией: «Поле — это вопрос системы к пользователю.
  А если строже — элемент формы с путём к данным…».
- **Живые персонификации сохраняем** («данные ждут», «форма получает данные»),
  но рядом — строгая версия.
- При выборе нового образа спросить: выдержит ли простой контрпример? не
  конфликтует ли с другими образами в этом же параграфе? уплотняется ли до
  одного предложения без потери силы?
- Каноничные и запрещённые образы фиксируются в `spec/constitution.md` каждой
  книги; менять — только через CHANGELOG.

## 5. Педагогические принципы

- **Одно новое за параграф.** Расширение уже введённого понятия — не «второе
  новое». Второе принципиально новое — сигнал разбить параграф.
- **Термин — награда, не входной билет.** Порядок: пример из жизни → мостик →
  ярлык-термин. Не открывать абзац незнакомым термином.
- **Упрощение = частный случай, не противоречие.** Позднее уточнение достраивает
  картинку, а не сносит её.
- **Учим на родном домене читателя** (телефон, кошелёк, расписание, склад
  «Канцтоваров»), второй домен — точечно и в минимальной дозе.
- **Никаких абсолютов** «без X нет Y» — через «возникает, когда…», «требует…».
  Это касается и технических утверждений.
- **Без антропоцентризма.** Если правило работает и для человека, и для
  программы — формулировать сразу для обоих.
- **Повторить вместо ссылки.** Нужное из прошлого параграфа повторяем кратко
  здесь, а не отсылаем «см. §A3». Ссылка — дополнение для углубления, не опора.
- **Нет висячего знания.** Не вводим понятие/синтаксис, который в параграфе не
  используется. Упоминание мимоходом — только с явной отсылкой, где раскроется.
- **Чередование нагрузки.** После плотного параграфа — заметно легче. Это
  методический выбор, не слабость.

## 6. Разметка и схемы

- Книга — **проза**. Жирный, курсив, списки — точечные акценты, не способ
  организации мысли. Если списки и жирный занимают больше четверти объёма —
  это презентация, а не книга.
  - **Жирный** — ключевые слова, которые надо запомнить.
  - *Курсив* — названия, цитаты, мягкие акценты.
  - Списки — только для действительно равноправных пунктов.
- **Ключевые мысли — якоря-выноски `>`** сразу, как только фраза стоит цитирования.
- Не дублировать системы выделения: якорь — `>`, термин — жирный/курсив по контексту.
- **ASCII-схемы — основа** (моноширинные, в кодовых блоках). **Mermaid** — только
  когда ASCII не справляется.
- **Эмодзи в основном тексте — никогда** (если автор явно не попросил).

## 7. Код и метаданные

- Каждый пример **компилируется и работает** (как минимум синтаксически).
- Имена переменных — **на русском**, описательные: `СтрокаТовара`, `НачалоПериода`,
  `ХешДвоичные`, не `х`/`result`.
- После каждой команды — `;`. Закрытие блоков — `КонецЕсли`, `КонецЦикла`,
  `КонецПроцедуры`. Комментарии — только через `//`.
- Параметры запроса — через `&Имя`, никогда не склейкой строк.
- **Комментарий объясняет «зачем» или результат**, не «что»: `// "510"`,
  не `// складываем строки`. Нетривиальная строка — с комментарием; листинг
  должен читаться как псевдокод.
- В блоке указываем язык: `bsl` (и `python`/`javascript`/`csharp` — в книгах
  сравнения).
- **Цитаты дерева метаданных** приводим как есть; синтаксис платформы
  (`РегистрСведений.<Имя>`) не меняем.

## 8. Терминология

- **Бытовой регистр → строгий термин в скобках:** «Отобрать (отбор, фильтрация)».
  Сначала бытовое слово, потом термин.
- **Перегрузка терминов — главный враг.** Слова, живущие в нескольких ролях
  («Остатки», «Период», «Движение», «Запись»), в одном абзаце в двух ролях не
  используем. Вводя слово в новой роли — сразу проговариваем смысл.
- В сквозном примере выбираем имена, не совпадающие с системными (регистр
  «ТоварыНаСкладах», не «ОстаткиТоваров»).
- **Аббревиатуры предметной области в прозе не вводим** — всегда полное название
  («регистр сведений», не «РС»). Исключения: код 1С, прямые цитаты дерева,
  заголовки таблиц сравнения.
- **Термины до официального ввода** — с оговоркой: «слово N здесь стоит мимоходом;
  вернёмся к нему в § X».

## 9. Чего не делать

- Не начинать параграф с «В данном разделе мы рассмотрим…».
- Не использовать пассив там, где можно активный.
- Не ставить вопрос без ответа в том же параграфе (кроме намеренного крючка — тогда явно).
- Не оставлять «висячих» обещаний «об этом позже» без указания, где именно.
- Не превращать учебник в IT-блог: без плакатных блоков и частокола подзаголовков.
- Не оставлять авторских метакомментариев в тексте параграфа (они — в `reviews/`).

## 10. Механическая проверка

Детерминированную часть канона проверяет линтер:

```bash
./book.sh lint            # всё в chapters/
./book.sh lint chapters/03_registry   # отдельный модуль
```

Он ловит: адресацию не по канону («ты», авторское «я»), аббревиатуры предметной
области в прозе, ссылки «см. §» вместо краткого повтора, канцелярит, шаблонные
зачины, пустые усиления, эмодзи и тяжёлое форматирование. Frontmatter, блоки
кода, инлайн-код и содержимое кавычек-ёлочек (имена объектов, цитаты дерева,
прямая речь персонажей) из проверки исключены.

Серьёзность каждого правила книга настраивает в `metadata.yaml`:

```yaml
style_lint:
  severity:
    address: warning    # error | warning | off
```

Так книга узаконивает осознанное отклонение от канона — но только записав его в
свою надстройку ниже и в `spec/decisions.md`.

**Честная граница:** линтер ловит дёшево и грубо. Перегрузку терминов, сломанные
метафоры и ощущение голоса судят панель ревью (`scripts/review.py`) и человек.

## 12. Сверка перед релизом

Каждое фактическое утверждение о платформе — особенно сигнатуры виртуальных
таблиц, имена служебных полей, значения свойств по умолчанию — сверять с
синтакс-помощником целевой версии 8.3.x. Спорное — помечать `FIXME` и выносить
в `reviews/*/synthesis.md` под «На сверку перед релизом».

## Надстройка книги «1С-разговорник»

Книга серии **«для опытных»**: читатель — действующий разработчик на Python,
JavaScript или C#, который переходит на 1С. Ядро канона действует полностью;
ниже — дельта.

### Что меняется относительно новичкового трека

- **Читатель знает программирование.** Переменные, циклы, типы, функции
  объяснять не нужно — нужно объяснять, чем они в 1С *отличаются*.
- **Опора на интуицию из других языков разрешена** — в новичковых книгах серии
  она запрещена. Здесь это основной инструмент: «в Python это list, но…».
- Темп выше, параграфы короче: 800–1500 слов.

### Структура параграфа (дельта)

1. **Связь с предыдущим** — 1–2 предложения.
2. **Основной материал**: как устроено в 1С → почему именно так.
3. **Таблица аналогий**: 1С / Python / JavaScript / C#.
4. **Блок «Ловушки при переходе»** — в конце параграфа, единым блоком, не
   разбросан по тексту.
5. **Якорная выноска `>`** с главной мыслью.

### Двусторонние примеры

Каждое существенное отличие показываем с двух сторон: как на 1С смотрит
питонист и как на Python смотрит 1С-разработчик. Односторонний взгляд оставляет
читателя с ощущением, что 1С — «неправильный Python».

### Код

- Язык блока указывается всегда: `bsl`, `python`, `javascript`, `csharp`.
- Комментарий объясняет результат: `// "510"`.
- Сравнительные листинги идут парой, одинаковой длины: слева задача, справа —
  та же задача на другом языке.

### Таблицы

Таблицы — только для сравнения языков. Для всего остального действует общее
правило канона: книга — проза.
